## 一、结论摘要

**交付模型维持基线 `M1_main_224/best.pt`（float32），不启用任何优化手段。** 三项实验全部完成实测，判定如下：

| 候选手段 | 体积变化 | CPU 前向变化 | 精度回退（宏观 F1） | 控制线（≤1 pp） | 启用判定 |
| --- | --- | --- | --- | --- | --- |
| 动态量化 int8（仅全连接层） | **−0.08%** | −4.65% | +0.000 pp | 通过 | ❌ **排除** |
| 静态量化 int8（Conv+Linear） | **−74.76%** | **−39.55%** | −0.962 pp | 通过（余量仅 0.038 pp） | ⏸ **暂不启用，列为储备** |
| 结构化剪枝 30% + 微调 | −30.31% | −22.61% | **−3.550 pp** | **超标** | ❌ **放弃** |

**判定的核心依据**（PRD §7.5 原文）：*"优化手段仅在推理耗时或模型体积未达目标时启用，不得为优化而优化。"*

| 启用条件 | 实测值 | 是否满足 |
| --- | --- | --- |

## 二、实验口径与纪律

所有对照必须在同一把尺子上完成，否则数字没有意义。本轮固定了四项口径：

| 项 | 口径 | 理由 |
| --- | --- | --- |
| 测试集 | `ml/dataset/split.json` 的 **test 划分，2,734 张**，冻结共用 | PRD §7.5「必须在同一测试集上完整复测」 |
| 预处理 | `ml/dataset/preprocess.py` 的 `build_eval_transform()`，确定性、无随机 | 与训练/推理链路单一来源，避免口径漂移 |
| 指标 | `ml/training/train.py` 的 `metrics_from_cm()`，与训练期同源 | 避免另写一套指标实现造成不可比 |
| 评估设备 | **一律 CPU** | int8 模型只能跑 CPU；若基线用 GPU、量化用 CPU，浮点累加顺序不同会引入不可比的微小偏差 |

校准数据纪律：静态量化的校准集使用 **val 划分**（512 张），不使用 test —— 与 PRD §7.4.3「阈值标定不使用测试集」同一纪律。
剪枝微调使用 train 划分，以 **val 划分**的宏观 F1 选最优权重，test 仅在最终复测时一次性使用。

## 四、量化实验

### 4.1 路径 A：动态量化（PRD §7.5 原文方案）

`torch.ao.quantization.quantize_dynamic(model, {nn.Linear}, dtype=torch.qint8)`，命中 1 个 Linear 模块（即分类头）。

| 指标 | 基线 | 动态量化 | 变化 |
| --- | --- | --- | --- |
| 体积 | 42.768 MB | 42.734 MB | **−0.08%** |
| CPU 前向 p50 | 16.654 ms | 15.880 ms | −4.65% |
| 测试集 acc | 0.996342 | 0.996342 | **+0.000 pp** |
| 测试集宏观 F1 | 0.967835 | 0.967835 | **+0.000 pp** |

**判定：排除。** 精度无损，但体积几乎不变、耗时改善在测量噪声量级。原因是结构性的：被量化的是占总参数 0.105% 的分类头，卷积主体仍是 float32；同时动态量化需在每次前向时对激活做运行时量化，本身就引入额外开销。
（早期在一次与 GPU 任务并行的环境下曾测得 CPU 耗时**上升 33%**，即负载干扰放大了该开销 —— 这也印证了「同进程统一测量」口径的必要性。）

### 4.2 路径 B：FX 静态量化（补充方案，超出 PRD §7.5 列举范围）

`quantize_fx.prepare_fx / convert_fx` + x86 后端，对 Conv 与 Linear 一并 int8 化，命中 14 个量化模块。校准 512 张（val 划分，7.6 s）。

| 指标 | 基线 | 静态量化 | 变化 |
| --- | --- | --- | --- |
| 体积 | 42.768 MB | **10.794 MB** | **−74.76%** |
| CPU 前向 p50 | 16.654 ms | **10.068 ms** | **−39.55%** |
| 测试集 acc | 0.996342 | 0.995245 | −0.110 pp |
| 测试集宏观 F1 | 0.967835 | 0.958218 | **−0.962 pp** |
| 硬指标（acc ≥0.85 / F1 ≥0.82） | 达标 | 达标 | — |

**为什么做这一条（超范围）**：PRD §7.5 把「需在 CPU 环境部署」列为启用条件，而 §7.6.1 的设备策略是「GPU 优先，显存不足时降级为 CPU 单图推理并告警」。即 CPU 路径确有业务含义，其可实现性需要数据支撑，不能靠推断。

**判定：暂不启用，列为储备方案。** 理由有三：
1. 精度回退 −0.962 pp 虽在 1 pp 控制线内，但**余量仅 0.038 pp** —— 换一台机器、换一批校准数据即可能超标，鲁棒性不足以作为交付依据；
2. 启用条件并不成立（GPU 耗时与体积均远优于目标）；
3. PRD §7.5 的决策基线是「宁可接受较慢的推理，也不接受精度跌破门槛」。**在无 CPU 部署需求的前提下，用 0.962 pp 的精度余量换取用不到的体积与速度收益，不符合该基线。**

关于 1 pp 控制线口径的提示：该控制线写于「优化是必要的」这一前提之下。对静态量化而言，真正可用的指标应是「CPU 部署场景下端到端是否满足 ≤3 s」—— 而 10.07 ms 的纯前向在任何情况下都远超所需。故此处保留判定结论，但标注该差异。

### 4.3 量化模型的分发方式（真实缺陷与解法）

**踩到的坑**：FX 静态量化模型用 `torch.save(model)` 整体落盘后**无法加载**：

```
AttributeError: 'ConvReLU2d' object has no attribute '_modules'
  ← torch/fx/graph_module.py: _deserialize_graph_module → KeepModules().trace()
```

根因：FX `GraphModule` 反序列化时会重新 trace，而量化融合后的算子（`ConvReLU2d` / `ConvBnReLU2d`）在 trace 路径下缺 `_modules` 属性。这不是配置问题，是 pickle 往返机制的固有限制 —— 也正因如此，PyTorch 官方推荐量化模型以 **state_dict 或 TorchScript** 分发。

**解法**：改为 `state_dict` + **重建配方**（qconfig backend + 固定 example 输入）。

```python
common.rebuild_static_int8_fx(base_model, state_path='.../state_dict.pt')
#   prepare_fx → 用固定随机数据跑 2 批（仅为让 convert_fx 不报错）
#   → convert_fx 固化结构 → load_state_dict 覆盖全部量化参数
```

关键认识：scale / zero_point 都是 **buffer**，会随 `state_dict` 被完整恢复，因此重建时**不需要真实校准数据**；而结构由 qconfig 与模型拓扑决定，与校准数据无关。

**往返自检（round-trip）**：落盘后立即重建并比对同一输入下的输出，实测**最大绝对差 0.000e+00 → PASS**。没有这一步，就只是"写了个文件"，并不知道它能不能用。

## 五、结构化剪枝实验

### 5.1 实现方式：按 stage 剪枝，而非按 block

以每个 stage 输出端 BatchNorm 的缩放因子 |γ|（Network Slimming 口径）作为通道重要性。

**关键设计决策**：剪枝单元取 **stage** 而非单个 block。残差结构要求同一 stage 内所有 block 的输出通道是**同一集合**（`out = conv2_out + identity` 需逐元素相加）。按 block 各自剪枝时，无 downsample 的 block（`layer1.1` / `layer2.1` / `layer3.1` / `layer4.1`）的恒等映射立刻维度错配，实测报错：

```
RuntimeError: The size of tensor a (45) must match the size of tensor b (64) at non-singleton dimension 1
```

按 stage 选定共同保留集后，stage 内恒等映射天然成立，**无需插入任何新模块、不改变网络拓扑**。另需同步缩减 **stem（conv1/bn1）** 的输出通道，否则 `layer1.0` 的恒等映射仍是 64→64 而 conv2 输出只有 45 —— 该坑在实现中实际踩中两次，第二次的根因正是这里。

**与「掩码式剪枝」的区别（重要）**：`torch.nn.utils.prune` 系列是掩码式 —— 权重置零但张量形状不变，**参数量、计算量、体积都不下降**，还会额外增加 mask buffer 使体积变大。而 PRD §7.5 的启用条件是「模型体积成为瓶颈」，掩码式剪枝对此毫无意义。故本轮实现**真正的结构重建**：

| 项 | 基线 | 剪枝 30% | 变化 |
| --- | --- | --- | --- |
| 参数量 | 11,188,311 | 7,791,978 | **−30.36%** |
| 体积 | 42.766 MB | 29.802 MB | **−30.31%** |
| 实际稀疏度 | — | 30.00%（960 通道剪掉 288） | — |
| 层末 conv 输出 / fc 输入 | 512 | 358 | — |

### 5.2 实现正确性验证（必须先做的一步）

在给出「剪枝后精度崩溃」的结论前，必须排除自身实现缺陷 —— 否则结论建立在错误前提上。

**验证方法**：`keep_map` 取全集（稀疏度 0%）时，重建模型应与基线**逐元素等价**。

| 项 | 结果 |
| --- | --- |
| 16 张样本最大逐元素绝对差 | **0.000e+00** |
| 判定 | **PASS —— 权重迁移完全正确** |

实现正确，故后续精度结论可归因于方法本身。

### 5.4 剪后微调与恢复

剪枝必然损伤精度，随后在训练集上微调 8 轮（Adam 差分学习率 lr_head=3e-4 / lr_backbone=3e-5，余弦退火，类别加权 + label_smoothing=0.1），以 val 宏观 F1 选最优：

| 轮次 | val acc | val 宏观 F1 |
| --- | --- | --- |
| （剪枝未微调） | 0.070958 | 0.011890 |
| ft01 | 0.9623 | 0.8370 |
| ft02 | 0.9667 | 0.8442 |
| ft03 | 0.9802 | 0.8919 |
| ft04 | 0.9821 | 0.8910 |
| ft05 | 0.9879 | 0.9244 |
| ft06 | 0.9876 | 0.9227 |
| **ft07（最优）** | **0.9898** | **0.9301** |
| ft08 | 0.9890 | 0.9265 |
| 基线对照 | 0.997074 | 0.975185 |

微调把模型从崩溃态救回，但 **val 宏观 F1 仍落后基线 4.51 pp**，且第 8 轮已进入平台（未收敛到控制线内）。

### 5.5 根因分析

1. **事后（post-hoc）剪枝缺乏稀疏化约束**：Network Slimming 之所以有效，前提是**训练时对 BN 的 γ 施加 L1 正则**，使 γ 真正承担「通道重要性」的语义。本轮直接对已训练模型的 γ 排序剪枝，γ 编码的是批归一化的缩放需求，而非通道的全局重要性 —— 「γ 小」不等于「可删」。
2. **网络没有可安全删除的冗余通道**：剪 1% 即崩 17.9 pp，说明重要性高度集中。M1 仅 11 个 epoch 就达到 val acc 0.9971，模型容量与任务匹配，不存在大批冗余通道。
3. **误差沿残差链放大**：删除某 stage 的通道会同时改变后续 block 的 `in_channels` 与 shortcut 切片，单通道信息缺失会在下游被放大。

**因此，「结构化剪枝不达标」不是稀疏度选得不好，而是该实现路径在本模型上的固有性质。**

## 七、为什么"优化推理"对本项目的端到端耗时几乎无意义

PRD §9.1.1 把 3 秒预算分解为：上传 200 + 预处理 200 + **推理 2000** + 落库 300 + 渲染 300 ms。M3 阶段的真实服务实测是：

| 环节 | 实测 | 占端到端 |
| --- | --- | --- |
| 端到端（自提交至结果返回） | **p50 44–55 ms**，max 60–78 ms | 100% |
| 其中纯前向推理 | 约 18–19 ms（GPU） | 约 40% |

把推理段彻底降到 0，端到端也只从约 50 ms 降到约 30 ms —— 而预算是 3000 ms。**换言之，端到端余量约 55–68 倍，瓶颈根本不在推理。**

这也解释了为什么本案的正确结论是「不启用优化」，而不是「优化效果不佳」：**三项手段都在优化一个不需要被优化的环节。**

## 八、结论

1. **交付模型维持基线 `ml/models/M1_main_224/best.pt`（float32），不做任何替换。** 后端 `SEATONG_MODEL_PATH` 与前端链路均**无需改动**，本轮不影响任何已验收的 M3/M4 成果。
   > **【V1.1 追记，2026-09-21】** 本条结论已被后续 OOD 评估推翻：基线在网图 OOD 上仅 32.26%，
   > 混合微调模型 `M1_ood_tuned/best.pt`（同分布零回退、OOD Top-1 82.80%）经用户裁决
   > **已替换为生产模型**。量化/剪枝排除结论不受影响。详见
   > `docs/海瞳鱼鉴-分布外网图评估报告.md` §6.1。
2. **动态量化：排除。** 只能影响占总参数 0.105% 的分类头，实测体积 −0.08%、CPU −4.65%，属可忽略量级。
3. **静态量化：暂不启用，列为储备。** 控制线内通过但余量仅 0.038 pp，且启用条件不成立。若未来出现「纯 CPU 环境部署」需求，它是唯一现成的可行方案（体积 −74.76%、CPU −39.55%，精度回退 0.962 pp），届时需重新校准并复核控制线。
4. **结构化剪枝：放弃。** 宏观 F1 回退 3.550 pp，超控制线 3.55 倍；且诊断曲线显示 1% 稀疏度即回退 17.879 pp，说明该手段在本模型上不适用于任何稀疏度，不是参数没调好。
5. **PRD §11.1 风险 R-T-04（量化/剪枝导致精度回退超限）已实测触发**：处置措施「超标即放弃该手段，保留未优化基线」**已按预案执行**。R-T-05（推理超 3 秒）与 R-T-08（模型体积过大加载慢）经实测**均不成立**。

## 十、局限与后续可选路径

### 方法学限制（须与结论一同引用）

1. **单次微调、无重复**：剪枝微调仅 8 轮且只跑一次，与 M2 对照实验同一限制，未给出置信区间。
2. **微调未收敛到底**：第 8 轮仍在缓升（0.9265 → 呈平台），**延长微调可能继续改善**。但以曲线斜率与已恢复幅度判断，要达到控制线内（val 宏观 F1 ≥0.9651）所需轮数远超当前量级，且需与「重训一个新模型」的成本比较 —— 后者更划算。
3. **CPU 耗时受系统负载影响**：同进程内的相对比较有效，绝对值波动约 ±10%（曾观测到并行 GPU 任务时基线 CPU 从 14.30 ms 升至 16.65 ms）。GPU 侧 2.2–2.6 ms 的差异同样在噪声范围内。
4. **未做量化感知训练（QAT）**：本轮的量化均为训练后量化（PTQ），QAT 通常可显著改善静态量化的精度回退，但需重新训练，本轮未投入。

### 后续可选路径（需裁决）

| 路径 | 内容 | 预估成本 | 可行性判断 |
| --- | --- | --- | --- |
| **A（推荐）** | **维持基线，不启用优化** | 0 | 与 PRD §7.5「不得为优化而优化」一致 |
| B | 稀疏化训练（BN γ 加 L1 正则，30 epoch）→ 剪枝 → 微调 | 约 30 分钟 GPU | 唯一可能让剪枝达标的路径；但优化收益本身仍无必要（见第七节） |
| C | 量化感知训练（QAT）改善静态量化 | 约 25 分钟 GPU | 仅在确定需要 CPU 部署时才有意义 |
| D | 补做「保护首层」剪枝对照 | 约 11 分钟 GPU | **不建议**：1% 稀疏度即崩 17.9 pp，已排除"首层是主因"的假设 |

**建议采纳 A，并把 B/C/D 登记为「已知可选项、当前不投入」，在项目说明与答辩材料中作为「按控制线纪律放弃优化」的案例呈现** —— 这比强行启用一个用不到的优化更能体现工程判断力。
