# 接口契约偏离诊断

_生成时间：2026-09-21 · 触发场景：M4 前端开工前契约核实_

## 一、结论速览

动手写前端前的契约核实暴露出一个**必须由需求方裁决**的架构级问题：

| 层级 | 端点文件 | 与后端实现的冲突数 |
|---|---|---|
| PRD §8.1 接口清单 | `docs/海瞳鱼鉴-PRD.md` | **14 处** |
| D8 API 接口契约 | `docs/海瞳鱼鉴-API接口契约.md` | **14 处** |
| D9 §10.4.4 关键接口对接清单 | `docs/海瞳鱼鉴-UIUX设计文档.md` | **12 处** |
| 后端实现 | `backend/app/api/*.py` | —（基准） |

**要害**：PRD §8.1 与 D8 **完全一致**（均为 27 个端点），说明后端在实现阶段**自主改动了路径体系**，但**未回写任何一份文档**。更严重的是，后端源码注释中声称自己对应「D8 §7 history / §8 result / §4 users 组」，而这些章节号与 D8 实际内容**不符** —— 即后端是在**误认 D8 内容**的前提下完成实现的。

**因此不能简单说「后端错了」**：后端 29 个端点已通过 206/206 断言（含真实 HTTP 联调），是**可运行的事实**。冲突的本质是**三份文档与一套实现互不承认**。

### 2.3 D9 相对 PRD 的额外错误

D9 §10.4.4 除继承 PRD 的 12 处冲突外，还有：

- D9 写 `GET /api/config` / `PUT /api/config` —— **丢失 `admin` 前缀**，与其自身 §5.12 页面规格（`/admin/config`）也不一致。
- D9 写 `POST /api/records/compare` —— **凭空发明**，PRD/D8/后端均无此端点。而 D9 自身 §5.8 定义了「对比视图」页面，即**页面规格依赖一个不存在的接口**。

## 三、根因分析

1. **PRD 与 D8 之间有强一致性**（27 = 27，逐行对应），说明这两份是同一套设计意图。
2. **后端实现偏离了两者**，且偏离方向一致（`records → history`、`admin/users → users`、去掉 batch、合并 guest/quota）。
3. **后端注释自称对应 D8**，但引用的章节号（§7/§8/§4）与 D8 实际结构不符 —— 表明后端是**独立设计路径**后补写的注释，而非照 D8 实现。
4. **D9 是在 PRD 基础上写的**，因此继承了 PRD 的写法；同时因未做端到端核实，产生了 §2.3 的额外错误。

**这不是笔误，是流程缺陷**：实现阶段完成 29 个端点、206 项验证后，**没有做「文档 ↔ 实现」的回归核对**，导致文档与代码分叉。D9 撰写时也未对后端做实测校验（`uiux_doc_verify.py` 的校验项只覆盖了令牌/路由/需求覆盖/Mermaid/格式，**不含接口路径**）。

## 四、三条可选处置路线

| 路线 | 做法 | 优点 | 代价 | 风险 |
|---|---|---|---|---|
| **A｜改文档对齐实现**（推荐） | 修订 PRD §8.1 与 D8，使其与后端 29 端点一致；同步修订 D9 §10.4.4 | 不动已验证的代码；一次修订三份文档即闭环 | 需改 3 份文档（PRD 27→29 行表、D8 全篇端点小节、D9 §10.4.4） | D8 有 2,453 行，端点散落各章，修订量较大 |
| **B｜改代码对齐文档** | 重写后端路由，回到 PRD 的 27 端点写法 | 文档体系保持原样 | 破坏已通过的 206 项验证；需重跑三层测试；且 PRD 的 `species_id` 与 D7 的 `class_index` 本就是 PRD 的错 | **高** —— PRD 自身有错（见下） |
| **C｜加兼容层** | 后端同时暴露两套路径（别名路由） | 前端可任选 | 端点翻倍，D8 的「端点唯一性」约束失效；技术债 | 中 |

### 关键事实：PRD 自身确有错误

**PRD 写 `GET /api/species/{species_id}`，但 D7 数据库设计中 `species` 表的主键是 `class_index`，不存在 `species_id` 字段。** 后端改用 `{class_index}` 是**修正**，不是偏离。这降低了路线 B 的合理性。

---

## 五、建议

**采用路线 A**，理由：

1. **代码是可运行事实**，已通过 206/206 断言 + 真实 HTTP 联调 + 23/23 真图识别正确。改动它需重跑全部验证，收益不成比例。
2. **后端多数改动是合理的**：`/api/history` 比 `/api/records` 语义更准（该资源确为「识别历史」）；`{class_index}` 修正了 PRD 的字段名错误；合并 `guest/quota` 进 `/api/users/me` 减少一次首屏请求（D9 §10.5 也要求「应用启动只调一个端点确定身份」）。
3. **但后端有 4 处功能缺口必须补**，不能仅改文档了事：
   - `DELETE /api/records/{record_id}` 单条删除 —— D9 §5.6 历史列表有单条删除入口
   - `GET/PATCH` 管理端跨用户记录访问 —— PRD FR-USER-08 明确要求
   - `POST /api/recognize/batch` —— PRD FR-RECOG-05 明确要求批量识别
   - 配置更新语义（单点 vs 批量）需统一
