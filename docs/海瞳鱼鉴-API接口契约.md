## 第 1 章　通用约定

### 1.1 基础信息

| 项 | 约定 |
| --- | --- |
| 接口前缀 | `/api` |
| 后端服务端口 | 8000 |
| 前端开发服务端口 | **5180** |
| 完整地址（开发环境） | `http://localhost:8000/api` |
| 内容类型 | 请求与响应均为 `application/json; charset=utf-8`；文件上传为 `multipart/form-data` |
| 字符编码 | 全链路 UTF-8。中文、拉丁学名均可直接传输，无需转义 |
| 时间格式 | 所有时间字段为 **Unix 时间戳（UTC 秒，整数）**。前端负责按用户本地时区格式化展示 |

**时间格式的说明**：数据库以 UTC 时间戳存储（见数据库设计文档第 2.3 节决策 4），接口层**不做转换，原样传递**。转换职责统一在前端，避免服务端时区与客户端时区混用导致的时间错位。前端展示时须显式按本地时区格式化，例如 `new Date(ts * 1000).toLocaleString()`。

### 1.2 请求头

| 请求头 | 必填 | 说明 |
| --- | --- | --- |
| `Content-Type` | 是（有请求体时） | `application/json` 或 `multipart/form-data` |
| `Authorization` | 按接口权限要求 | `Bearer <access_token>` |
| `Accept` | 否 | 默认 `application/json` |
| `X-Request-Id` | 否 | 客户端可传入追踪标识；未传时服务端自动生成 |

**关于 `Authorization` 的强制要求**：令牌**禁止置于 URL 查询参数**（PRD 第 8.2 节）。置于 URL 会被浏览器历史、代理日志与 Referer 头记录，构成泄漏渠道。该要求须在代码评审时作为检查项。

### 1.3 分页约定

需要分页的接口统一使用以下查询参数：

| 参数 | 类型 | 默认值 | 取值范围 | 说明 |
| --- | --- | --- | --- | --- |
| `page` | int | 1 | ≥ 1 | 页码，从 1 开始 |
| `page_size` | int | 20 | 1 ～ 100 | 每页条数 |

分页响应体的 `data` 部分结构固定：

```json
{
  "items": [],
  "total": 137,
  "page": 1,
  "page_size": 20,
  "total_pages": 7
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `items` | array | 当前页数据项 |
| `total` | int | 满足筛选条件的总条数（**非当前页条数**） |
| `page` | int | 当前页码 |
| `page_size` | int | 每页条数 |
| `total_pages` | int | 总页数，等于 `ceil(total / page_size)` |

**`total` 的语义须明确**：它是筛选后的总数，而非全表总数。前端的分页控件须据此渲染，否则筛选后页数会显示错误。

**越界行为**：`page` 超出 `total_pages` 时返回空 `items` 数组，HTTP 状态仍为 200，**不报错**。理由是页码越界属正常交互（如用户删除末页最后一条后停留在原页码），报错会增加前端处理负担。

### 1.4 排序约定

| 接口 | 排序字段 | 方向 | 是否可改 |
| --- | --- | --- | --- |
| `GET /api/records` | `created_at` | 降序（最新在前） | 可传 `sort` 参数改为升序 |
| `GET /api/records/export` | `created_at` | 升序（便于阅读） | 否 |
| `GET /api/admin/users` | `created_at` | 降序 | 否 |
| `GET /api/admin/records` | `created_at` | 降序 | 否 |
| `GET /api/species` | `class_index` | 升序 | 否 |

**物种清单的排序为 `class_index` 升序，不可改为其他顺序**。理由见 PRD 第 6.4.3 节：`class_index` 是全系统对齐键，任何按中文名拼音或拉丁名字母序的排序都会破坏模型输出与展示的对应关系。前端若需按名称排序，**须在前端本地排序**，不得请求服务端改变顺序。

### 1.5 幂等性

| 端点 | 幂等 | 说明 |
| --- | --- | --- |
| `POST /api/images` | 否 | 重复上传产生新的图像资产记录 |
| `POST /api/recognize` | 否 | 每次调用都是一次新的识别，消耗额度 |
| `DELETE /api/records/{record_id}` | **是** | 重复删除同一记录返回成功（软删除已是幂等） |
| `PUT /api/admin/config` | **是** | 全量覆盖配置，重复提交结果一致 |
| `PATCH /api/admin/users/{user_id}` | **是** | 设置目标状态，重复提交结果一致 |
| 其余 | 否 | 按常规语义 |

**重试需谨慎的端点**：`POST /api/recognize` 与 `POST /api/recognize/batch` 会消耗游客额度。**前端不得对这两个端点做自动重试**——网络异常后自动重试会导致额度被扣两次。正确做法是提示用户手动重试，或先在服务端做请求去重（见第 11.5 节 EC-05）。

### 1.6 跨域配置

后端按配置项 `SEATONG_FRONTEND_ORIGIN` 放行来源列表，开发环境实际允许 `http://localhost:5180`、`http://127.0.0.1:5180`（并保留 5173 / 5174 兼容其他联调场景）。生产环境须显式配置实际域名，**不得使用通配符 `*`**——携带 `Authorization` 头的请求本身要求来源显式声明。

> **实现口径说明（M6 联调核实）**：本节原写作 `SEATONG_CORS_ORIGINS`（复数、列表语义），
> 后端实现为单值配置项 `SEATONG_FRONTEND_ORIGIN`（`backend/app/core/config.py`），
> 主允许源取该值，其余开发源在 `backend/app/main.py` 的 `CORSMiddleware` 中显式列出。
> 二者语义等价但名称不同，属命名偏离，已登记（见《集成联调与验收记录》偏差表）。

## 第 2 章　认证与鉴权

### 2.1 令牌方案

采用 **JWT 双令牌**方案（PRD 第 8.2 节）：

| 令牌 | 用途 | 有效期 | 传递方式 |
| --- | --- | --- | --- |
| 访问令牌（access token） | 访问业务接口 | 2 小时 | `Authorization: Bearer <token>` |
| 刷新令牌（refresh token） | 换取新的访问令牌 | 7 天 | 请求体字段 `refresh_token` |

**双令牌的理由**：若仅用单个长有效期令牌，泄漏后的风险窗口过长；若仅用短令牌，用户需频繁重新登录。双令牌使访问令牌可短、刷新令牌可长，兼顾安全与体验。

### 2.2 访问令牌载荷

```json
{
  "sub": "7",
  "username": "lulu",
  "role": "user",
  "iat": 1789630000,
  "exp": 1789637200,
  "jti": "b1f2c3d4-5e6f-7a8b-9c0d-1e2f3a4b5c6d"
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `sub` | string | 用户标识，取 `user.id` |
| `username` | string | 用户名，便于日志标识 |
| `role` | string | `user` / `admin` |
| `iat` | int | 签发时间戳 |
| `exp` | int | 过期时间戳 |
| `jti` | string | 令牌唯一标识，用于登出时加入失效集合 |

**载荷中禁止出现的字段**：密码哈希、邮箱、真实姓名、上传记录等任何敏感或可关联身份的信息（PRD 第 8.2 节明确要求）。**JWT 载荷是 Base64 编码而非加密，任何持有者均可解码阅读**。这一点须在实现时牢记。

### 2.3 令牌刷新流程

```
前端                          后端
  │                             │
  ├─ 请求业务接口 ─────────────►│
  │                             │ 校验访问令牌
  │◄─── 40102 令牌已过期 ───────┤
  │                             │
  ├─ POST /api/auth/refresh ───►│ 校验刷新令牌
  │   { refresh_token }         │
  │◄─── 新访问令牌 + 新刷新令牌 ─┤
  │                             │
  ├─ 重放原请求 ───────────────►│
  │◄─── 正常响应 ───────────────┤
```

**关键约束**：

1. **刷新须静默完成**，用户无感知。前端在响应拦截器中统一处理 40102。
2. **原请求须重放一次**，且**仅重放一次**。若刷新后仍返回 40102，不得再次刷新，应直接跳转登录页——否则会形成无限循环。
3. **刷新令牌亦失效**时跳转登录页，并**保留原路径**，登录后跳回。
4. **并发请求的处理**：若多个请求同时收到 40102，应共用一次刷新操作，而非各自发起刷新。多个刷新请求会导致刷新令牌轮换冲突（见第 2.4 节）。

### 2.4 刷新令牌轮换

每次刷新**同时签发新的访问令牌与新的刷新令牌**，旧刷新令牌立即失效。

**轮换的理由**：若刷新令牌可重复使用，一旦泄漏，攻击者可在 7 天内持续获取访问令牌而受害者无从察觉。轮换使刷新令牌成为一次性凭据，重复使用会暴露异常。

**前端须注意**：收到新刷新令牌后必须**覆盖本地存储的旧值**。若遗漏此步，下次刷新会因使用失效令牌而失败，表现为"用户每隔 2 小时被登出一次"。

### 2.5 角色与权限

| 角色 | 标识 | 权限范围 |
| --- | --- | --- |
| 普通用户 | `user` | 本人数据（图像、记录、导出）、公开接口 |
| 管理员 | `admin` | 全部用户数据、系统配置、操作日志；同时拥有普通用户全部权限 |
| 游客 | 未登录 | 仅公开接口，识别受试用次数限制（默认 3 次） |

**权限校验的落点**：**全部在服务端**。前端隐藏入口仅是界面优化，**不构成安全手段**（PRD 第 8.2 节明确）。任何"前端已隐藏按钮"作为权限保障的做法均视为缺陷。

### 2.6 越权防护

PRD 第 8.2 节要求：访问他人资源时**不泄露资源是否存在**。

| 场景 | 响应 | 说明 |
| --- | --- | --- |
| 请求他人存在的识别记录 | `40401` 资源不存在 | 与下一行**返回完全相同的响应** |
| 请求不存在的识别记录 | `40401` 资源不存在 | **与上一行不可区分** |
| 请求本人不存在的记录 | `40401` 资源不存在 | 同样返回 `40401` |

**这一设计的理由**：若"他人的记录"返回 403 而"不存在的记录"返回 404，攻击者可通过遍历 ID 判断哪些记录真实存在，从而推断出平台的数据规模与活跃度。**统一返回 `40401` 可消除该信息泄漏。**

> **★ 关于"403 还是 404"的澄清（V1.1 更正）**：本节的 V1.0 版本曾写"PRD 要求返回 **403**"，并据此规定三行均返回 `40301`。**该表述方向相反，已更正。**
>
> 真正的判别准则只有一条：**对"他人资源"一律返回 `40401`**。理由是返回 403 会泄露"该 ID 存在但不是你的"，恰恰破坏 PRD「防 ID 枚举」的本意；返回 404 才能让"不存在"与"无权访问"真的不可区分。
>
> **`40301` 的适用场景因此收窄为三类**（均与"资源归属"无关）：
> 1. 非管理员访问管理端点（角色不足）；
> 2. 管理员对自身账号执行被禁止的操作（如 9.5 删除自己）；
> 3. 权限校验以外的语义性拒绝（如 9.4 重置其他管理员密码，`40904` 也取 403）。
>
> 实测证据：以用户 B 的令牌访问用户 A 的记录详情 / 记录删除 / Top-5 候选 / 原图 / 缩略图，五者**全部返回 `404` + `40401`**。

**实现要点**：查询须带 `WHERE user_id = <当前用户>` 条件。若查不到，**无论该 ID 是否真实存在，一律返回 `40401`** —— 实现上**不应**再额外查一次"该 ID 是否存在"，因为那会引入一个不必要的信息分支。管理员访问任意资源不受此限制。

### 2.7 登录失败锁定

| 项 | 规则 |
| --- | --- |
| 触发条件 | 连续登录失败 **5 次** |
| 锁定时长 | **10 分钟** |
| 计数字段 | `user.failed_login_count` |
| 锁定字段 | `user.locked_until` |
| 成功登录 | **须将 `failed_login_count` 归零** |

**归零的必要性**：若成功登录后不归零，计数会跨多次成功登录累积，导致用户偶发失败几次后意外被锁定，且难以复现。

**用户不存在时的处理**：用户名不存在时应**同样返回 `40103` 用户名或密码不正确**，不返回"用户不存在"。理由与第 2.6 节相同——避免通过登录接口枚举有效用户名。

**锁定期间**：返回 `40105`，响应中可含剩余锁定秒数，提示用户等待。**不得提示"密码错误"**，否则会误导用户反复尝试。

### 2.8 登出

`POST /api/auth/logout` 将当前访问令牌的 `jti` 加入服务端失效集合，前端同步清除本地存储的两个令牌。

**失效集合的实现**：因采用 JWT（无状态），服务端无法"撤销"已签发的令牌，须维护一个失效 `jti` 集合并在校验时查询。该集合可存于内存（重启后失效）或数据库。**本项目规模下建议内存存储**，并在第 11.5 节 EC-06 中记录该取舍的后果：服务重启后旧令牌会短暂恢复有效，直至自然过期。若需严格保证，须改为持久化存储。

## 第 3 章　统一响应结构

### 3.1 成功响应

```json
{
  "code": 0,
  "message": "ok",
  "data": { },
  "request_id": "7f3a1c9e-2b4d-4e88-9a01-5c6d7e8f9a0b"
}
```

### 3.2 失败响应

```json
{
  "code": 40001,
  "message": "username 长度须为 4 ～ 20 位",
  "data": null,
  "request_id": "7f3a1c9e-2b4d-4e88-9a01-5c6d7e8f9a0b"
}
```

### 3.3 字段定义

| 字段 | 类型 | 必含 | 说明 |
| --- | --- | --- | --- |
| `code` | int | 是 | 0 表示成功；非 0 为错误码（第 4 章） |
| `message` | string | 是 | 用户可读说明；成功时为 `ok` |
| `data` | object / array / null | 是 | 业务数据；失败时为 `null` |
| `request_id` | string | 是 | 请求追踪标识，与日志中的同一字段对应 |

**`request_id` 的用途**：用户报错时提供该编号，运维可在日志中定位完整调用链。错误响应中 `message` 可附该编号（见 `50001` 的处置）。

**`message` 的语言**：统一为**中文**，面向最终用户，可直接展示。**不得包含堆栈、SQL 语句、文件路径等实现细节**（NFR-SEC-05）。技术细节只进日志，不进响应。

### 3.4 HTTP 状态码与业务码的关系

| 层 | 职责 |
| --- | --- |
| HTTP 状态码 | 表达**请求的处理结果类别**（400 参数错、401 未认证、403 无权限、404 不存在、409 冲突、413 过大、415 类型错、422 语义错、429 限流、500 服务端错、503 不可用） |
| 业务码 `code` | 表达**具体错误原因**，粒度细于 HTTP 状态码 |

**两者须同时正确**。仅设置业务码而 HTTP 状态统一返回 200 的做法**不可接受**——它会使浏览器、代理、监控工具无法识别错误，也会让前端的错误处理退化。第 4 章的总表逐行给出两者的对应关系，实现时须严格遵循。

## 第 4 章　错误码总表

本文档展开 PRD 第 8.3.2 节的错误码，并在其基础上补充管理端业务约束码，**共 21 个**。**码值只增不改**：已发布的码值语义不得变更，新增场景使用新码值。

### 4.1 参数与认证类

| 码值 | 含义 | HTTP | 触发条件 | 前端处置 |
| --- | --- | --- | --- | --- |
| `40001` | 请求参数缺失或格式错误 | 400 | 必填字段缺失、类型不符、取值越界 | 字段级提示，标出具体字段名 |
| `40101` | 未登录或令牌无效 | 401 | 缺少 `Authorization` 头、令牌签名错误、令牌已登出 | 引导登录，保留原路径 |
| `40102` | 访问令牌已过期 | 401 | 令牌 `exp` 已过 | **静默刷新令牌后重试一次** |
| `40103` | 用户名或密码不正确 | 401 | 登录时凭据不符，**或用户名不存在** | 就地提示，不区分账号是否存在 |
| `40104` | 账号已被禁用 | 401 | `user.status = 0` | 提示联系管理员 |
| `40105` | 账号已锁定 | 401 | `locked_until` 未到期 | 提示剩余锁定时间 |
| `40301` | 无权访问该资源 | 403 | **仅用于角色不足或语义性拒绝**：非管理员访问管理端点、管理员操作自身账号、重置其他管理员密码、删除自己。**不用于"资源属于他人"**（那走 `40401`） | 提示无权限 |
| `40401` | 资源不存在 | 404 | 资源不存在，**或存在但属于他人**（两者对外不可区分，防 ID 枚举） | 展示空态或错误页 |
| `40901` | 用户名已存在 | 409 | 注册时 `username` 冲突（忽略大小写） | 注册表单就地提示 |
| `40902` | 不允许禁用自身账号 | 409 | 管理端禁用自己（`user_id` 等于当前登录用户） | 提示不可禁用自身 |
| `40903` | 不允许禁用最后一个管理员 | 409 | 目标为最后一个 `role='admin' AND status=1` 的账号 | 提示须先启用其他管理员 |
| `40904` | 不允许重置其他管理员密码 | 403 | 管理端重置其他管理员账号的密码 | 提示须由该账号本人操作 |

**`40902` ～ `40904` 的归属说明**：三个码值同属「违反业务约束」语义。`40902` 与 `40903` 为**冲突段**（操作与系统既有状态冲突），HTTP 取 409；`40904` 语义上更接近**权限拒绝**（虽码值落在 `409xx` 段，但 HTTP 取 403），此前曾在两处取值间摇摆，**现按「权限语义优先」定为 403**，理由见第 9.4 节与第 11.5 节 EC-02。

### 4.2 上传与识别类

| 码值 | 含义 | HTTP | 触发条件 | 前端处置 |
| --- | --- | --- | --- | --- |
| `41301` | 文件体积超过上限 | 413 | 单文件 > 10 MB，或单批文件数 > 9 | 提示实际大小与上限值 |
| `41501` | 文件类型不支持 | 415 | 内容判定结果不在允许类型内 | 提示支持的格式清单 |
| `42201` | 图像无法解码 | 422 | 内容判定通过但解码失败（文件损坏、截断） | 提示文件损坏或格式异常 |
| `42202` | 图像分辨率过低 | 422 | 任一边 < 64 px | 提示分辨率要求 |
| `42901` | 游客试用额度已用尽 | 429 | 游客 `usage_count` 达到上限 | 引导注册 |
| `42902` | 请求过于频繁 | 429 | 超出速率限制 | 提示稍后重试 |

**`41301` 的两种触发**：单文件超限与单批数量超限**共用同一码值**。前端可通过 `message` 区分，或自行在提交前校验数量。两种情形都属"超出上限"，共用码值符合语义。

**`42201` 与 `41501` 的区别**：`41501` 是**类型不在允许清单内**（如上传了 PDF）；`42201` 是**类型允许但内容损坏**（如截断的 PNG）。二者不可混用——前者提示用户换格式，后者提示用户换文件。

### 4.3 服务端类

| 码值 | 含义 | HTTP | 触发条件 | 前端处置 |
| --- | --- | --- | --- | --- |
| `50001` | 服务端内部错误 | 500 | 未捕获异常 | 提示「服务暂时不可用」，附追踪编号 |
| `50301` | 识别服务暂不可用 | 503 | 模型未加载或加载失败 | 提示稍后重试 |
| `50302` | 请求队列已满 | 503 | 并发请求超出处理能力 | 提示当前请求较多 |

**`50301` 与 `50001` 的区别**：`50001` 是意外错误，`50301` 是**已知的可恢复状态**（模型未就绪）。分开表达使前端可给出更准确的提示，也使监控能区分两类告警。

### 4.4 错误码分段规则

| 段 | 区间 | 语义 |
| --- | --- | --- |
| 参数段 | `400xx` | 客户端请求有误 |
| 认证段 | `401xx` | 身份未确认或凭据不符 |
| 权限段 | `403xx` | 身份已确认但无权访问 |
| 不存在段 | `404xx` | 资源不存在 |
| 冲突段 | `409xx` | 与既有数据冲突 |
| 体积段 | `413xx` | 请求体过大 |
| 类型段 | `415xx` | 媒体类型不受支持 |
| 语义段 | `422xx` | 语法正确但语义不可处理 |
| 限流段 | `429xx` | 请求频率或额度超限 |
| 服务端段 | `500xx` | 服务端内部错误 |
| 不可用段 | `503xx` | 服务暂时不可用 |

**分段规则的作用**：新增错误码时按段归属，避免码值语义混乱。例如日后若需"图像包含非法内容"的错误，应归入 `422xx` 段并取新值 `42203`，而非复用已有码值。

### 5.1 `POST /api/auth/register` 注册并自动登录

| 项 | 内容 |
| --- | --- |
| 权限 | 公开 |
| 关联需求 | FR-USER-01 |
| 幂等 | 否 |

**请求体**

| 字段 | 类型 | 必填 | 约束 | 说明 |
| --- | --- | --- | --- | --- |
| `username` | string | 是 | 4 ～ 20 位，字母、数字、下划线 | 登录名，查重**忽略大小写** |
| `password` | string | 是 | 8 ～ 32 位，须含字母与数字 | 明文传输，服务端 bcrypt 哈希后存储 |
| `nickname` | string | 是 | 2 ～ 20 字符 | 昵称 |
| `email` | string | 否 | 合法邮箱格式，≤ 120 字符 | 选填 |

**请求示例**

```json
{
  "username": "lulu",
  "password": "Seatong2026",
  "nickname": "噜噜",
  "email": "lulu@example.com"
}
```

**响应 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `access_token` | string | 访问令牌，有效期 2 小时 |
| `refresh_token` | string | 刷新令牌，有效期 7 天 |
| `token_type` | string | 固定为 `Bearer` |
| `expires_in` | int | 访问令牌剩余有效秒数（7200） |
| `user` | object | 用户信息，结构见第 5.5 节 |

**状态码**

| 场景 | HTTP | 业务码 |
| --- | --- | --- |
| 成功 | 201 | 0 |
| 参数不合规 | 400 | `40001` |
| 用户名已存在 | 409 | `40901` |
| 用户名格式或长度不符 | 400 | `40001` |

**业务规则**

- 用户名查重**忽略大小写**：已存在 `lulu` 时，`Lulu` 与 `LULU` 均视为冲突（BR-USER-01）。该规则由数据库的函数唯一索引 `idx_user_username_lower` 保证（见数据库设计文档第 4.2 节）。
- 注册成功后**直接签发令牌**，用户无需再登录一次（"自动登录"）。
- 密码**不得记录到任何日志**，包括调试日志（NFR-SEC-05）。

### 5.2 `POST /api/auth/login` 登录并签发令牌

| 项 | 内容 |
| --- | --- |
| 权限 | 公开 |
| 关联需求 | FR-USER-02 |
| 幂等 | 否 |

**请求体**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `username` | string | 是 | 登录名，**大小写不敏感** |
| `password` | string | 是 | 明文密码 |

**响应 `data`**：与第 5.1 节相同结构（`access_token`、`refresh_token`、`token_type`、`expires_in`、`user`）。

**状态码**

| 场景 | HTTP | 业务码 |
| --- | --- | --- |
| 成功 | 200 | 0 |
| 凭据不符 | 401 | `40103` |
| 账号被禁用 | 401 | `40104` |
| 账号锁定中 | 401 | `40105` |
| 参数缺失 | 400 | `40001` |

**业务规则**

- **用户名不存在与密码错误返回相同响应**（均 `40103`），防止通过登录接口枚举有效用户名。
- 连续失败 5 次锁定 10 分钟（第 2.7 节）。
- **登录成功须将 `failed_login_count` 归零**。
- 登录成功须写入 `operation_log`（`action = 'login'`），失败不写（避免被用作日志膨胀攻击）。

### 5.3 `POST /api/auth/logout` 登出

| 项 | 内容 |
| --- | --- |
| 权限 | 需登录 |
| 关联需求 | FR-USER-03 |
| 幂等 | 是（重复登出返回成功） |

**请求体**：无。

**响应 `data`**：`null`。

**状态码**

| 场景 | HTTP | 业务码 |
| --- | --- | --- |
| 成功 | 200 | 0 |
| 未登录或令牌无效 | 401 | `40101` |

**业务规则**

### 5.4 `POST /api/auth/refresh` 刷新令牌

| 项 | 内容 |
| --- | --- |
| 权限 | 携带刷新令牌（无需访问令牌） |
| 关联需求 | FR-USER-02 |
| 幂等 | 否 |

**请求体**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `refresh_token` | string | 是 | 登录或上次刷新时获得的刷新令牌 |

**响应 `data`**：新的 `access_token` 与**新的 `refresh_token`**，结构同第 5.1 节。

**状态码**

| 场景 | HTTP | 业务码 |
| --- | --- | --- |
| 成功 | 200 | 0 |
| 刷新令牌无效或过期 | 401 | `40101` |
| 账号已被禁用 | 401 | `40104` |

**业务规则**

- **刷新令牌一次性使用**：每次刷新同时签发新刷新令牌，旧令牌立即失效（第 2.4 节）。
- 刷新时**须重新校验账号状态**：若账号在令牌有效期内被禁用，刷新应返回 `40104` 而非签发新令牌。

| 项 | 内容 |
| --- | --- |
| 权限 | 需登录 |
| 关联需求 | FR-USER-05 |
| 幂等 | 否 |

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |

| 场景 | HTTP | 业务码 |

### 5.8 `GET /api/guest/quota` 查询游客剩余额度

| 项 | 内容 |
| --- | --- |
| 权限 | 公开 |
| 关联需求 | FR-USER-06 |
| 幂等 | 是 |

**请求参数**：无。游客会话由服务端依据请求生成或识别，**不依赖客户端传入会话标识**。

**响应 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `limit` | int | 试用次数上限，取自 `system_config.guest_trial_limit`（默认 3） |
| `used` | int | 已使用次数 |
| `remaining` | int | 剩余次数，等于 `limit - used`，**不小于 0** |

**响应示例**

```json
{
  "code": 0,
  "message": "ok",
  "data": { "limit": 3, "used": 1, "remaining": 2 },

}
```

**业务规则**

- 额度**在服务端计数**（`guest_usage` 表），确保清理浏览器本地存储无法绕过限制（BR-USER-12）。

- `remaining` 计算须做**下限截断**：若管理员下调了上限（如从 3 改为 1），已有 `used = 3` 的会话 `remaining` 应为 `0` 而非 `-2`。

| 类型判定 | **以文件内容为准，扩展名仅作辅助** | BR-UPLOAD-01 |

**响应 `data`**

| --- | --- | --- |

| `failed` | array | 失败项列表 |
| `total` | int | 提交总数 |
| `success_count` | int | 成功数 |
| `fail_count` | int | 失败数 |

**`succeeded` 项结构**

| 字段 | 类型 | 说明 |
| --- | --- | --- |

| `original_filename` | string | 原始文件名 |
| `file_size` | int | 字节数 |
| `width` | int / null | 宽度，解码后回填 |
| `height` | int / null | 高度，解码后回填 |
| `mime_type` | string | 服务端判定的类型 |
| `is_duplicate` | bool | 是否与本人既有图像内容重复 |

**`failed` 项结构**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `original_filename` | string | 原始文件名 |
| `code` | int | 错误码（`41301` / `41501` / `42201` / `42202`） |
| `message` | string | 失败原因 |

**状态码**

| 场景 | HTTP | 业务码 |
| --- | --- | --- |
| 全部成功 | 200 | 0 |
| 部分成功 | 200 | 0（**HTTP 仍为 200**） |
| 全部失败 | 400 | 首个失败项的错误码 |
| 超出单批数量 | 413 | `41301` |

**关键设计：部分失败返回 200**

批量上传时"部分成功"是**正常的业务结果**，不是请求错误。若返回 4xx，前端的通用错误处理会把整个请求判为失败，导致成功上传的文件无法被使用。因此：

- **只要有一个文件成功，HTTP 状态即为 200**，失败详情在 `failed` 数组中（BR-UPLOAD-04）。
- 前端须**分别处理** `succeeded` 与 `failed`：成功的进入预览待识别，失败的逐条提示。
- **全部失败时**返回 400，`code` 取首个失败项的错误码，`data` 中仍包含完整 `failed` 数组。

**业务规则**

- 上传**不消耗**游客识别额度——额度在识别时扣减（见第 6.2 节）。理由是上传后用户可能未执行识别，此时扣减额度对用户不公平。
- **重复检测**：`content_hash` 与本人既有图像相同时标记 `is_duplicate = true`，**但仍正常保存并返回**。是否跳过识别由前端决定并提示用户（BR-UPLOAD-07）。
- 存储文件名使用 UUID，**不使用用户原始文件名**（PRD 第 6.5 节）。原始文件名仅存于数据库。
- **游客上传的记录 `user_id` 为空**，须有清理机制（`expires_at`）。

| 字段 | 类型 | 必填 | 约束 | 说明 |
| --- | --- | --- | --- | --- |
| `image_ids` | string[] | 是 | 1 ～ 9 个 | 待识别的图像标识列表 |

**响应 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `results` | array | 逐图结果，**顺序与请求一致** |
| `total_duration_ms` | int | 总耗时 |
| `success_count` | int | 成功数 |
| `fail_count` | int | 失败数 |

**`results` 项结构**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `image_id` | string | 图像标识 |
| `success` | bool | 是否成功 |
| `data` | object / null | 成功时为单图识别的 `data` 结构（第 6.2 节） |
| `code` | int / null | 失败时的错误码 |
| `message` | string / null | 失败原因 |

**状态码**

| 场景 | HTTP | 业务码 |
| --- | --- | --- |
| 全部成功 | 200 | 0 |
| 部分成功 | 200 | 0（HTTP 仍为 200） |
| 全部失败 | 400 | 首个失败项的错误码 |
| 数量超出上限 | 400 | `40001` |

**业务规则**

- **顺序执行**，非并发。理由是单机 GPU 推理下并发会导致显存争用与耗时抖动，顺序执行的总耗时反而更稳定可预期（见数据库设计文档与 PRD 第 7 章的单机部署基线）。
- **额度按成功识别数扣减**，而非按提交数扣减。若提交 5 张、成功 4 张，扣 4 次。
- **超出剩余额度时的行为**：游客剩余 2 次但提交 5 张时，**只识别前 2 张**，其余返回 `42901`。不整体拒绝——已上传的图像应得到处理，整体拒绝会浪费用户的等待。
- `results` 的顺序**必须与 `image_ids` 一致**，即使中间有失败项。前端据此将结果与预览图对应。
- **部分失败返回 200**，理由同第 6.1 节。

### 6.4 `GET /api/images/{image_id}/content` 获取原图

| 项 | 内容 |
| --- | --- |
| 权限 | 需登录且归属校验 |
| 关联需求 | FR-RESULT-04 |
| 响应类型 | 图像二进制流 |

**路径参数**

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `image_id` | string | 图像标识（UUID） |

**响应**

| 项 | 内容 |
| --- | --- |
| `Content-Type` | 图像的实际 MIME 类型 |
| `Content-Length` | 字节数 |
| 响应体 | 图像二进制数据 |
| `Cache-Control` | `private, max-age=86400` |

**状态码**

| 场景 | HTTP | 业务码 |
| --- | --- | --- |
| 成功 | 200 | —（直接返回二进制） |
| 未登录 | 401 | `40101` |
| 图像不存在，**或存在但非本人** | 404 | `40401` |
| 原图已过留存期被清理 | 404 | `40401` |

**关键设计说明**

1. **本接口返回二进制而非 JSON 统一结构**。图像内容无法嵌入 JSON 信封而保持可用，故本端点是全文**唯一的例外**。失败时仍返回 JSON 错误结构。
2. **原图不通过静态目录暴露**（PRD 第 8.1.2 节）：所有图像访问经本接口鉴权。若直接将 `SEATONG_UPLOAD_DIR` 挂载为静态目录，任何人猜到文件名即可访问他人图像。
3. **`Cache-Control: private`** 而非 `public`：图像属用户私有，禁止中间代理缓存。`max-age=86400` 允许浏览器本地缓存 1 天，减少重复请求。
4. **归属校验**：查询须同时匹配 `image_id` 与 `user_id`。管理员不受此限制。
5. **过期图像的处置**：原图超留存期（默认 180 天）已被清理时，返回 404。**此时识别记录仍在**，前端应展示"原图已过留存期"的提示而非空白。这一点须在结果页与历史详情页统一处理。
6. **鉴权查询参数兜底（V1.3 增补）**：`<img>` 等浏览器原生请求无法携带 `Authorization` 请求头，本端点（与 6.5）额外接受 `?access_token=<JWT>` 查询参数；游客场景接受 `?guest_session=<session_id>`（与 `X-Guest-Session` 请求头同语义）。**仅限图像二进制端点使用**——常规 JSON 接口禁止把令牌放进 URL（避免落入访问日志），鉴权依赖实现上仅对可选登录端点开放该兜底。

### 6.5 `GET /api/images/{image_id}/thumb` 获取缩略图

| 项 | 内容 |
| --- | --- |
| 权限 | 登录且归属校验（游客持会话可读取本人上传的图） |
| 关联需求 | FR-RESULT-02、FR-HISTORY-02 |
| 内容类型 | `image/jpeg` |
| 幂等 | 是 |

**路径参数**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `image_id` | string(uuid) | 是 | 图像资产 ID |

**查询参数**

| 参数 | 类型 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `size` | int | 否 | `320` | 缩略图长边像素。服务端**钳制到 `[64, 1024]`**，越界值不报错而是截断 |
| `access_token` | string | 否 | — | JWT 查询参数兜底，仅供 `<img>` 标签使用（见 6.4 说明 6）。请求头优先，二者只取其一 |
| `guest_session` | string | 否 | — | 游客会话兜底，语义同 `X-Guest-Session` 请求头 |

**响应**

返回 JPEG 二进制，带 `X-Skip-Envelope: 1` 跳过 JSON 信封。失败时返回 JSON 错误结构。

**关键设计说明**

1. **本端点返回二进制，与 6.4 同属统一响应结构的例外**。
2. **引入动机**：历史列表与结果页需要展示图像预览。若直接复用 6.4 的原图端点，列表页会拉取多张原图（单张可达 10 MB），在弱网下完全不可用。缩略图将单张传输量压到数十 KB 量级。
3. **长边语义**：`size` 约束的是**长边**而非宽高各自的值，以保证不同宽高比的图像在列表中视觉尺寸一致。
4. **缓存更激进**：`Cache-Control: private, max-age=86400`。缩略图是从原图派生的确定性结果，内容不会变化，可放心长缓存。
5. **与 6.4 共用归属校验**：两端的鉴权逻辑完全相同，实现上应复用同一函数，避免一处修好另一处遗漏。

### 6.6 `DELETE /api/images/{image_id}` 删除图像资产

| 项 | 内容 |
| --- | --- |
| 权限 | 登录且归属校验（**不向游客开放**，理由见下） |
| 关联需求 | FR-UPLOAD-08（上传清理） |
| 幂等 | 是（重复删除返回 `40401`） |

**路径参数**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `image_id` | string(uuid) | 是 | 图像资产 ID |

**请求体**：无。

**响应 `data`**：`null`。`message` 为 `图片已删除`。

**响应示例**

```json
{
  "code": 0,
  "message": "图片已删除",
  "data": null,
  "request_id": "9d2e4f6a-3c5b-4d71-8e92-0a1b2c3d4e5f"
}
```

**错误**

| 业务码 | HTTP | 触发条件 |
| --- | --- | --- |
| `40101` | 401 | 未登录 |
| `40401` | 404 | 图像不存在，**或存在但非本人所有**（见下） |
| `42201` | 422 | 图片已产生识别记录（见下） |

**业务规则**

1. **只允许删除尚未产生识别记录的图片。** 一旦 `recognition_record.image_id` 指向本图，返回 `42201` 并提示「该图片已产生识别记录，请改用历史记录的删除功能」。
   - **理由**：`recognition_record.image_id` 对 `image_asset` 是 **CASCADE** 外键（见数据库设计文档）。若允许删除已有识别记录的图片，会**级联删掉用户的历史记录** —— 那是数据丢失，不是"清理"。历史记录的删除须走 7.3 的单条删除（软删除语义），保留可追溯性。
2. **不向游客开放。** 游客上传的图 `user_id` 为 `NULL`（`image_asset` 未存 `session_id`），服务端无法安全判定"这张图是你的"。若开放，任何持有 UUID 的人都可删除他人上传的图。游客图的清理交由留存期到期回收任务统一处理。
3. **归属校验返回 `40401` 而非 `40301`。** 对"他人资源"一律返回 `40401`，避免通过状态码差异泄露 ID 是否存在（防 ID 枚举）。`40301` 只用于"已认证但角色不足"。
4. **管理员可删除任意图片**（`40301` 不适用），但同样受第 1 条约束。
5. **执行顺序**：先删磁盘文件，再删数据库行。反序会在文件删除失败时留下无法定位的孤儿文件。
6. **本端点与识别链路无关**，不消耗游客额度，也不影响历史记录（因为已识别图被拒绝）。

> **与 6.1 上传的关系**：6.1 的上传**按 `(user_id, content_hash)` 复用资产**。若用户上传一张与既有图片字节完全相同的图，服务端返回既有资产（响应中 `reused: true`）而**不新建记录**。此时对该 `image_id` 执行删除，删除的是那张既有资产 —— 若它已有识别记录，则同样返回 `42201`。

| 场景 | HTTP | 业务码 |
| --- | --- | --- |
| 成功 | 200 | 0 |
| 未登录 | 401 | `40101` |
| 参数不合规 | 400 | `40001` |

**业务规则**

- **必须排除已软删除记录**（`is_deleted = 1`）。该条件须下沉到数据访问层默认过滤器，避免逐处遗漏（见数据库设计文档第 3.4 节）。
- **只能返回本人记录**：查询须带 `user_id = <当前用户>` 条件。这是越权防护的落点（NFR-SEC-03）。
- **筛选条件为 AND 关系**，多个条件同时生效。
- `start_date` 与 `end_date` 均为**闭区间**（含边界）。
- **索引支撑**：`(user_id, created_at DESC)` 复合索引服务于本接口的默认查询；`top1_species_id` 索引服务于 `species_id` 筛选（见数据库设计文档第 4.1 节）。
- **`thumbnail_available` 的作用**：原图超留存期被清理后 `image_asset` 记录可能仍在（或已级联删除）。前端据该字段决定是否渲染缩略图，避免产生大量 404 请求。

| 幂等 | **是** |

**路径参数**

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `record_id` | string | 记录标识 |

**响应 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `deleted_count` | int | 实际删除数，成功为 1 |
| `already_deleted` | bool | 是否本就已删除（幂等重放时为 `true`） |

### 7.4 `DELETE /api/records` 批量删除

| 项 | 内容 |
| --- | --- |
| 权限 | 需登录 |
| 关联需求 | FR-HISTORY-06 |
| 幂等 | 是 |

**请求体**

| 字段 | 类型 | 必填 | 约束 | 说明 |
| --- | --- | --- | --- | --- |
| `record_ids` | string[] | 是 | 1 ～ 100 个 | 待删除的记录标识列表 |

**响应 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `deleted_count` | int | 实际删除数 |
| `skipped_count` | int | 跳过数（不属于本人或已删除） |

**业务规则**

- **不存在的 ID 与属于他人的 ID 均计入 `skipped_count`，不报错**。理由有二：① 批量操作中个别 ID 失效属正常；② 若对"他人的 ID"单独报错，会泄漏该 ID 是否存在（第 2.6 节）。**两者合并计入跳过数，对外表现一致。**
- 单批上限 100，超出返回 `40001`。
- 使用 `DELETE` 携带请求体：虽然 HTTP 规范对 DELETE 带体存在争议，但主流框架均支持。**本方案已被采纳并验证通过**——实现所用 FastAPI 0.141.1 可正常解析 DELETE 请求体，无需退化为 `POST /api/records/batch-delete`。**该备选方案已否决**，理由是它会破坏本组端点的 REST 语义一致性，且引入一个"看起来像创建、实际是删除"的误导性路径。

| 项 | 内容 |

**响应**

| 项 | 内容 |
| --- | --- |

**CSV 列定义**

| 列序 | 列名 | 数据来源 |
| --- | --- | --- |
| 1 | 记录编号 | `record_id` |
| 2 | 原图文件名 | `original_filename` |
| 3 | 识别物种 | Top-1 中文名 |
| 4 | 拉丁学名 | Top-1 拉丁学名 |
| 5 | 置信度 | Top-1 概率，百分比保留 1 位小数 |
| 6 | Top-5 摘要 | 形如 `A:62.1% \| B:18.3% \| C:9.7% \| D:5.2% \| E:3.1%` |

- **导出须记入操作日志**（`action = 'export'`）。
- 无数据时**返回仅含表头的 CSV 而非 404**，使 Excel 打开后仍能看出列结构。

```json
    { "rank": 4, "class_index": 21, "cn_name": "黄纹炮弹鱼",
      "latin_name": "Balistapus undulatus", "confidence": 0.004176 },
    { "rank": 5, "class_index": 2, "cn_name": "长棘光鳃鱼",
      "latin_name": "Chromis chrysura", "confidence": 0.003682 }

  "request_id": "1a2b3c4d-5e6f-4a7b-8c9d-0e1f2a3b4c5d"

```

| 业务码 | HTTP | 触发条件 |
| --- | --- | --- |
| `40101` | 401 | 未登录 |
| `40401` | 404 | 记录不存在，或存在但非本人所有 |

**业务规则**

1. **候选数据从 `recognition_record.candidates_json` 读取**，不重新推理。这个字段在识别成功时一次性写入（见 6.2），故本端点是**纯读取**，耗时在毫秒级。
2. **`candidates_json` 存储在记录行内而非独立表**（决策基线）。理由是候选固定 5 条、只随记录读取、从不单独查询 —— 拆表只会增加一次 JOIN 而无收益。
3. **`confidence` 之和可能小于 1**。Softmax 在 23 类上归一化，Top-5 只取前 5 名，剩余 18 类的概率总和未包含在内。
4. **`rank` 与数组下标的一致性**：约定 `rank` 从 1 起，数组索引从 0 起。前端须显式使用 `rank` 字段而非依赖下标，避免一方从 0 起另一方从 1 起造成错位。
5. **`class_index` 是对齐键**：本端点的 `class_index`、`/api/species/{species_id}` 的 `species_id`、以及模型输出层的索引**三者必须同值**。这是全文最关键的不变量，任何一处偏移都会导致"识别正确但显示错物种"。
6. **`cn_name` 与 `latin_name` 是冗余字段**：前端本可拿着 `class_index` 再调物种接口取名字，但那会让结果页多一次往返。这里直接内联，**代价是物种改名时须保证两处同步**（物种名的唯一权威源见 11.3 节）。

### 7.7 路径别名 `/api/history*` 说明

| 项 | 内容 |

**业务规则**

- **`status` 的取值是 `ok` 而非 `healthy`。** 早期文档曾写作 `healthy` / `degraded` / `unhealthy`，**与实现不符，已更正**。当前实现在数据库可用时返回 `ok`；数据库不可用时整体请求失败（返回 `50001`）而非降级为 `unhealthy`。
- **模型状态是嵌套在 `model` 下，不是顶层扁平字段。** 这一点是**已发生的实现缺陷来源**：前端曾把 `getHealth()` 的类型写成扁平 `ready`，导致顶栏"服务正常"徽标永远显示为"服务维护中"（`h.ready` 恒为 `undefined`）。前端契约核验脚本已加入对该嵌套结构的**专项守护断言**。
- **`model.ready = false` 时识别接口返回 `50301`**，前端应据本接口提前判断，避免用户上传后才发现不可用。
- **`db_pragmas.foreign_keys` 是外键生效的直接证据。** 该值为 `0` 意味着级联删除、RESTRICT 保护全部失效 —— 须立即视为故障。

- **`device` 字段的用途**：本项目为单机部署、GPU 优先 CPU 可降级（决策基线）。该字段使运维能确认实际推理设备，避免"以为在用 GPU 实际在跑 CPU"导致的性能误判。
- **`ckpt` 字段暴露服务器绝对路径**，属信息泄露面。当前为单机部署、受众为学生与教师，接受该风险；若日后对外部署，应改为返回文件名或脱敏路径。

**状态码**

| 场景 | HTTP | 业务码 |

> **`40901` 的复用说明**：本项目的 `409xx` 段语义为「与既有数据冲突」。`40901` 在第 4 章中的定义为「用户名已存在」，用于注册场景。**本节的防护（禁用自身、禁用最后一个管理员）不应复用 `40901`**——语义不同。正确做法是按第 4.4 节的分段规则，为「违反业务约束」新增 `40902`（禁止禁用自身）与 `40903`（禁止禁用最后一个管理员），并在第 4 章总表中补录。**该补充已补入第 4.1 节**，判断记录见 11.5 节 EC-01。
>
> **`40903` 的跨端点复用**：9.5 的「删除用户」同样需要「不允许删除最后一个管理员」的保护，因此**复用 `40903`**。这不是码值滥用——两个端点的约束语义完全相同（都不能让管理员归零），故共用同一码值是正确的。相对的，删除场景还需「不允许删除自己」，该约束**复用 `40301`** 而非新增码值，因为它属于"已认证但无权对本目标执行该操作"的角色/身份判定，与 9.3 的 `40902`（冲突语义）不同：禁用是**可逆**的状态冲突，删除是**不可逆**的权限拒绝。

**业务规则**

- **禁止禁用自身**：管理员误禁用自己将导致管理入口关闭，而本项目**不提供密码找回**（决策基线），恢复只能直接改库。属必要的防呆设计。
- **保证至少一个可用管理员**：若目标是最后一个 `role='admin' AND status=1` 的账号，拒绝操作。两条约束互为补充——前者防自我锁定，后者防集体锁定。
- **禁用在下一次请求鉴权时生效**：鉴权中间件每请求校验 `user.status`，不单独维护禁用名单。延迟最多一个请求周期，对本项目安全要求足够。
- **禁用不删除数据**：历史记录与上传图像均保留，仅阻止登录。与「删除账号」是完全不同的语义。

- **越权边界**：管理员可重置普通用户与自己的密码，**不可重置其他管理员账号的密码**，避免管理员之间互相锁定。若确需为其他管理员重置，须由该账号本人操作或直接改库。该约束需新增码值，见 EC-02。
- **本操作必须写入 `operation_log`**：这是 `NFR-SEC` 中「敏感管理操作可追溯」的落点。本项目除识别记录外，`operation_log` 是唯一的审计线索来源。

| --- | --- | --- |
| `40101` | 401 | 未登录 |
| `40301` | 403 | 非管理员，**或试图删除自己的账号** |
| `40401` | 404 | 目标用户不存在 |

**业务规则**

1. **不允许删除自己的账号**，返回 `40301`，提示 `不能删除自己的账号`。
   - **理由**：管理员删除自己会立即失去后台访问权，且若他是最后一个管理员，系统将无人可管理。这条约束比"禁用自己"更强，因为删除**不可逆**。
2. **不允许删除最后一个管理员**，返回 `40903`。与 9.3 的禁用保护同源 —— 保证系统始终至少有一个可用的管理员账号。
   - **两条保护的差别**：`40301` 拦的是"删自己"（身份相关，任何人删自己都拦）；`40903` 拦的是"删掉最后一个管理员"（数量相关，删别人但会导致管理员归零才拦）。当唯一管理员删自己时，**`40301` 先触发**（身份判断在前）。
3. **删除用户时的数据处置**（外键级联规则，详见数据库设计文档 5.2 节）：

   | 关联数据 | 外键行为 | 结果 |
   | --- | --- | --- |
   | `image_asset.user_id` | `SET NULL` | 图像资产**保留**，归属置空（仍在磁盘上） |
   | `recognition_record.user_id` | `CASCADE` | 该用户的识别记录**全部删除** |
   | `operation_log.user_id` | `SET NULL` | 审计日志**保留**，归属置空（见 9.10 第 1 条） |
   | `guest_usage` | 无外键 | 不受影响（以 `session_id` 为主键） |

   > **这是本系统唯一会级联删除业务数据的入口。** 图像资产因 `SET NULL` 而残留为无主孤儿文件，**须由留存期回收任务清理**，不在本端点的职责内。管理员在界面上的确认文案必须明确提示"将同时删除该用户的 N 条识别记录"。
4. **物理删除而非软删除**。用户行被真正移除，不可恢复。这与识别记录的删除语义（见 9.6）不同 —— 后者是软删除。
5. **写入审计日志**（`action = 'delete'`，`target_type = 'user'`）。日志写入须在删除事务**之前或同一事务内**完成，避免用户已删而日志未记。
6. **删除审计日志自身归属的处理**：由于 `operation_log.user_id` 是 `SET NULL`，日志会保留但 `user_id` 变 `null`。为此日志的 `detail` 字段内联了当时的用户名（见 9.10 第 4 条），使"谁被操作"仍可读。

| 场景 | HTTP | 业务码 |
| --- | --- | --- |
| 成功 | 200 | 0 |

1. **`total_records` 与 `total_uploads` 不必相等。** 一张图可被多次识别（每次产生新记录），且上传后未识别的图只计入 `total_uploads`。两者的差值本身是有意义的运营信号。
2. **`top_species` 固定返回 5 项**（不足 5 个物种时按实际数量返回）。按 `count` 降序。排序相同时以 `class_index` 升序作**稳定次序**，避免同一份数据两次请求返回不同顺序。
3. **`top_species` 的 `cn_name` 来自物种元数据**，不入库到统计侧。这保证了改名后统计展示同步更新。
4. **`records_today` 用服务器本地时区的自然日边界**，不是 UTC、也不是滚动 24 小时。单机部署场景下该口径与运维直觉一致。
5. **`avg_duration_ms` 在无记录时返回 `0`**，不返回 `null` —— 前端可直接参与数值运算而不必判空。
6. **本端点不返回趋势序列**（如近 7 日曲线）。折线图需要按日聚合查询，属"日后可扩展"范畴，当前版本不实现。

6. **按 `action` 与 `user_id` 过滤可组合**，两者之间是 AND 关系。
7. **不要用本端点做实时监控轮询**：`total` 随每次请求增长，且分页查询在大表上有成本。运维监控应使用 8.3 健康检查。

## 第 10 章　文件上传约定

本章展开 PRD 第 8.4 节。上传是本系统唯一的二进制数据入口，也是格式伪装、超大文件、批量部分失败、路径穿越四类问题最集中的环节，故单列一章把约束写死。

---

### 10.1 涉及上传的端点

| 端点 | 位置 | 字段名 | 数量 | 权限 |
| --- | --- | --- | --- | --- |
| `POST /api/images` | 第 6.1 节 | `file` | 1 ～ 9 | 公开（游客限次） |
| `POST /api/recognize` | 第 6.2 节 | 无（传 `image_id`） | — | 公开（游客限次） |
| `POST /api/recognize/batch` | 第 6.3 节 | 无（传 `image_ids`） | — | 公开（游客限次） |

> **上传与识别分离是本契约的核心设计**。PRD 第 8.1 节将「上传图像」与「执行识别」拆为 `POST /api/images` 与 `POST /api/recognize` 两个端点。这与常见的一步式「上传即识别」不同，理由有三：
>
> 1. **解耦重试**：识别失败（如 `50301` 模型未加载）时用户可重试识别而无需重新上传。
> 2. **批量语义自然**：先上传 9 张得到 9 个 `image_id`，再决定单张还是批量识别。
> 3. **为预处理预览留出空间**：用户可先上传查看系统预处理结果，再执行识别。
>
> **代价是多一次往返**。在 3 秒端到端预算内（决策基线），前端可将上传与识别串行发起，实际感受仍是一次操作。

---

### 10.2 上传请求格式

**单张上传**

```

Host: 127.0.0.1:8000
Authorization: Bearer <access_token>
Content-Type: multipart/form-data; boundary=----WebKitFormBoundaryX7kQ2mZ

------WebKitFormBoundaryX7kQ2mZ
Content-Disposition: form-data; name="file"; filename="coral_reef_0117.png"
Content-Type: image/png

<二进制数据>
------WebKitFormBoundaryX7kQ2mZ--
```

**多张上传（同一字段名重复）**

```
POST /api/images HTTP/1.1
Host: 127.0.0.1:8000
Content-Type: multipart/form-data; boundary=----WebKitFormBoundaryY8nR3aP

------WebKitFormBoundaryY8nR3aP
Content-Disposition: form-data; name="file"; filename="a.png"
Content-Type: image/png

<二进制数据>
------WebKitFormBoundaryY8nR3aP
Content-Disposition: form-data; name="file"; filename="b.jpg"
Content-Type: image/jpeg

<二进制数据>
------WebKitFormBoundaryY8nR3aP--
```

**规范要求**

| 项目 | 要求 |
| --- | --- |
| 字段名 | 固定为 `file`（单张与多张**共用同一字段名**，重复出现） |
| 文件名 | 必须携带 `filename`，仅作元数据保存，**绝不参与磁盘路径拼接** |
| 数量 | 1 ～ 9 张；> 9 返回 `41301` |
| 空文件 | 0 字节视为非法，返回 `42201` |
| 编码 | 二进制传输，不要求 Base64 包装 |

> **为何单张与多张共用 `file` 字段而非另设 `files`**：PRD 第 8.1 节将两者合并为同一端点 `POST /api/images`，服务端按重复字段数判定数量。该设计使前端只需一套上传逻辑（`FormData.append("file", f)` 循环），无需按数量分支。数量信息在响应 `data.image_ids` 的数组长度中体现。

### 10.3 文件类型与内容校验

**允许的类型（白名单）**

| MIME 类型 | 扩展名 | 说明 |
| --- | --- | --- |
| `image/jpeg` | `.jpg` `.jpeg` | 常规照片格式 |
| `image/png` | `.png` | Fish4Knowledge 数据集原生格式 |
| `image/bmp` | `.bmp` | 无压缩位图 |
| `image/webp` | `.webp` | 现代网页格式 |

**不支持**：GIF（动图首帧语义不明确）、TIFF（OpenCV 读取行为依版本而异）、SVG（矢量格式，本质是 XML，存在外部实体注入风险），以及任何非图像类型。

**校验必须基于内容，不能基于扩展名**

攻击者可将任意文件改名为 `.png` 上传，仅检查扩展名或客户端声明的 `Content-Type` 均可被绕过。正确顺序：

1. **读取文件头魔数**，与白名单比对：

   | 格式 | 魔数（十六进制） |
   | --- | --- |
   | JPEG | `FF D8 FF` |
   | PNG | `89 50 4E 47 0D 0A 1A 0A` |
   | BMP | `42 4D`（`BM`） |
   | WebP | `52 49 46 46`（`RIFF`）+ 偏移 8 处为 `57 45 42 50`（`WEBP`） |

2. **用 Pillow 打开并执行 `verify()`**，确认结构完整、非截断文件。

3. **读取尺寸**，限制长边 ≤ 8000 px、短边 ≥ 64 px。

4. **实际解码一次**（`Image.open(...).convert("RGB")`），确保不是「头部合法但数据段损坏」的构造文件。

**为何第 4 步不可省**：`verify()` 只检查结构完整性，不做完整解码。构造一个头部合法、IDAT 数据块损坏的 PNG 可通过前 3 步，却会在预处理阶段抛异常，使错误从「上传阶段」漂移到「识别阶段」，错误码定位随之变差。

**校验失败的错误码**

| 场景 | HTTP | 业务码 |
| --- | --- | --- |
| 类型不在白名单（含伪装文件） | 415 | `41501` |
| 图像无法解码（含 0 字节空文件） | 422 | `42201` |
| 分辨率过低（任一边 < 64 px） | 422 | `42202` |
| 体积超限或数量超限 | 413 | `41301` |

> **为何「伪装文件」归入 `41501` 而非单独编码**：魔数不符意味着**实际类型不在允许清单内**，与上传 PDF 的语义相同。第 4 章明确 `41501` 是「类型不在允许清单」，`42201` 是「类型允许但内容损坏」，二者不可混用。

---

### 10.4 体积限制

| 限制项 | 值 | 依据 |
| --- | --- | --- |
| 单文件体积 | ≤ 10 MB | 决策基线锁定，不可上调 |
| 单批数量 | ≤ 9 张 | 决策基线锁定 |
| 单次请求总体积 | ≤ 90 MB | 9 × 10 MB 理论上限 |
| 最小分辨率 | 任一边 ≥ 64 px | `42202` |
| 最大分辨率 | 任一边 ≤ 8000 px | 防止解码内存膨胀 |

**三重校验点**

| 层级 | 位置 | 作用 |
| --- | --- | --- |
| 1 | 前端 | 选择文件后立即校验，超限直接提示、不发请求。**这是体验层，不构成安全边界** |
| 2 | ASGI 中间件 | 读取请求体时按 `max_file_size_mb` 截断，避免超大文件占满内存 |
| 3 | 应用层 | 逐文件核对体积，超限返回 `41301` |

**第 2 层不可省**：若只在应用层校验，Starlette 会先把整个请求体读入内存或临时文件才轮到业务代码执行，攻击者上传 1 GB 文件即造成内存压力。中间件层截断是真正的防线。

**中间件截断的响应要求**：须返回第 3 章定义的统一错误体（`code = 41301`），**不允许**把 Web 服务器的默认 413 HTML 页面透出给前端，否则前端的错误处理分支会因响应不是 JSON 而失效。

### 10.5 存储约定

**存储路径**

```
${SEATONG_IMAGE_DIR}/                    # 环境变量，见第 1.1 节
├── 2026/
│   └── 09/
│       └── 20/
│           ├── 3f2a1c9e-2b4d-4e88-9a01-5c6d7e8f9a0b.png
│           └── 7b4e6f1d-9a3c-4f55-8e72-1d2c3b4a5968.jpg
```

**命名规则**：`{uuid4}.{ext}`。

| 规则 | 依据 |
| --- | --- |
| 使用 UUID4 而非原始文件名 | 原始文件名可能重复、含路径分隔符、含非 ASCII 字符。**从根源消除路径穿越与文件名冲突** |
| 保留扩展名 | 便于运维识别类型；扩展名来自**魔数判定结果**，非用户提交的 `filename` |
| 按 `年/月/日` 三级目录 | 单目录文件数过多会降低 `readdir` 性能，亦便于按日期归档。本项目单机部署，三级足够 |
| 目录不存在时自动创建 | `os.makedirs(..., exist_ok=True)` |

**原始文件名**：保存在 `image_asset.original_filename` 列，仅用于展示。存储前须去除路径分隔符与控制字符，并截断至 255 字符。

**路径安全三条禁令**

1. **禁止**用用户提交的 `filename` 拼接存储路径。
2. **禁止**构造路径后不做归一化校验。必须执行 `os.path.realpath(target)` 并断言其仍在 `${SEATONG_IMAGE_DIR}` 之内。
3. **禁止**在获取图像内容的端点接受任意路径参数。`GET /api/images/{image_id}/content` 只能通过 `image_id` 查库得到存储路径，**不接受客户端传入路径**。

**`storage_path` 永不出现在任何响应中**：该列是服务端内部实现细节，暴露后会固化文件存储结构，使未来改变存储布局成为破坏性变更。

### 10.6 多张上传的部分失败语义

`POST /api/images` 一次可提交 1 ～ 9 张，其部分失败语义需明确定义。

**逐文件独立处理**：每个文件独立走「类型校验 → 体积校验 → 解码 → 落库」流程。单个文件失败**不回滚**其他文件，也不中断整批。

**HTTP 状态码的两种情形**

| 情形 | HTTP | 说明 |
| --- | --- | --- |
| 请求格式合法，但部分文件校验失败 | **200** | 返回 `code = 0`，`data` 中含 `fail_count` 与失败明细 |
| 请求格式非法（字段名错、全部文件都不合法） | **400** | 返回 `code = 40001` 或对应业务码 |

**为何部分失败返回 200**：若转为非 2xx，前端需同时处理「HTTP 错误」与「部分失败明细」两条路径，而用户真正关心的是「哪几张成功了」。统一 200 使前端逻辑收敛为一条：读 `data`，按 `success_count` 与 `fail_count` 分别渲染。

**响应 `data`（第 6.1 节的完整结构）**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `image_ids` | array&lt;string&gt; | 成功上传的图像标识，顺序与提交顺序一致 |
| `success_count` | int | 成功数量 |
| `fail_count` | int | 失败数量（`success_count + fail_count` = 提交总数） |
| `failed` | array | 失败明细 |
| `failed[].filename` | string | 失败文件的原始文件名 |
| `failed[].reason` | string | 失败原因描述 |
| `failed[].code` | int | 对应业务码（`41301` / `41501` / `42201` / `42202`） |

**响应示例**

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "image_ids": [
      "e5f6a7b8-0005-4000-8000-000000000005",
      "f6a7b8c9-0006-4000-8000-000000000006"
    ],
    "success_count": 2,
    "fail_count": 1,
    "failed": [
      {
        "filename": "broken.png",
        "reason": "图像无法解码，文件可能已损坏",
        "code": 42201
      }
    ]
  },
  "request_id": "f192b4e8-a3c5-41ee-2079-3e4f50617283"
}
```

**全部失败时**：HTTP 状态取**第一个失败文件的业务码对应的 HTTP 状态**（如首张类型非法则为 415），`code` 为该业务码，`message` 说明全部失败。**这属于请求错误，不是空结果**，与部分失败的 200 语义不同。

**游客试用次数的扣减口径**

| 情形 | 扣减 |
| --- | --- |
| 文件校验失败（`41301` / `41501` / `42201` / `42202`） | **不扣减**（未消耗推理资源） |
| 上传成功但后续识别失败（`50301`） | **不扣减**（系统侧故障） |
| 上传成功且识别成功 | 每成功 1 张扣减 1 次 |

> **关键区分**：`POST /api/images` 本身**不消耗**游客额度——它只落盘不解码推理。额度在 `POST /api/recognize` 与 `POST /api/recognize/batch` 成功返回时扣减（见第 6.2、6.3 节）。该分离使「上传了但未识别」不浪费用户额度。

**额度不足时的部分处理**：若游客剩余 `n` 次而批量识别提交 `m` 张（`m > n`），则**前 `n` 张正常识别，其余 `m - n` 张在 `results` 中返回失败项，`code = 42901`**。该策略优于整批拒绝，避免对用户已上传的图片做无谓丢弃，且返回结构与成功情形一致。

### 10.8 前端侧的上传约束

本节条目由契约直接推导而来，一并明确以避免前后端理解分歧。

| 约束 | 值 | 依据 |
| --- | --- | --- |
| `accept` 属性 | `.jpg,.jpeg,.png,.bmp,.webp` | 与 10.3 白名单一致 |
| 单文件预校验 | > 10 MB 时本地提示，不发请求 | 10.4 第 1 层 |
| 选择上限 | 9 张 | 10.4 |
| 请求超时 | 上传 60 s；单图识别 30 s；批量识别 120 s | 见下 |
| 并发控制 | 同一用户的识别请求一次仅 1 个在途 | 单机 GPU 串行推理 |

**超时值的三档设定依据**

- **上传 60 s**：9 张 × 10 MB 在局域网内的理论上限约 90 MB，按 1.5 MB/s 保守带宽估计约 60 s。该值只约束传输，与推理无关。
- **单图识别 30 s**：决策基线中的「单图端到端 ≤ 3 s」是**正常路径指标**（`NFR-PERF-01`）。30 s 是容错上限，为模型首次加载、CPU 降级运行等慢路径留出空间。
- **批量识别 120 s**：9 张串行推理的理论下限为 27 s（9 × 3 s），加落库开销后 120 s 是合理上限。**若按 30 s 设定，正常的大批量提交会被前端主动中断，产生「明明能成功却报超时」的假故障。**

### 11.3 字段与数据模型的一致性

本契约所有响应字段名须与数据库设计文档的列名保持可追溯关系。

| 规则 | 说明 |
| --- | --- |
| 同名词直接映射 | `user.username` → 响应 `username`，不改名 |
| 标识字段仍用 `_id` 后缀 | `image_id`、`record_id`、`species_id`、`user_id` 均保留后缀 |
| 主键对外的类型 | `user` / `image_asset` / `recognition_record` 的主键对外表示为 **string 类型标识**（示例中使用 UUID 形式），非自增整数。`species_id` 为整数（对应 `class_index + 1`） |
| 不暴露内部列 | `password_hash`、`failed_login_count`、`locked_until`、`storage_path` 永不出现在任何响应中 |
| 时间统一为时间戳（秒） | 与数据库 `INTEGER` 存储一致，避免字符串解析歧义。**唯一例外**：CSV 导出使用可读时间格式（见 7.5 节） |
| 枚举值口径 | `status` 为 `0` / `1` 整数；`role` 为 `user` / `admin` 字符串。与数据库 CHECK 约束一致 |

**候选结果字段的口径**：响应中的 `candidates` 数组由 `recognition_record` 的候选数据反序列化而来。**该字段在数据库中以 JSON 文本形式存储在单列中，而非独立表**（取舍说明见数据库设计文档 3.4 节）。因此响应中的数组形式是**服务端反序列化的结果**。存储中只保留 `class_index` 与 `probability`，物种中英文名与拉丁名在查询时关联 `species` 表得到——避免物种改名后历史记录的候选名称不同步。

**字段命名对照（响应 ↔ 数据库）**

### 11.4 一致性约束清单

以下约束跨越多个端点，集中列出以便实现时统一处理。

| 编号 | 约束 | 涉及端点 |
| --- | --- | --- |
| C-01 | `candidates` 数组长度恒为 5（`top_k` 固定，BR-RESULT-01） | 10、11、16、20 |
| C-02 | 所有时间字段为时间戳（秒）整数；CSV 导出除外 | 全部 |
| C-03 | 分页响应结构一致：`total` / `page` / `page_size` / `total_pages` / `items` | 15、25、30、33 |
| C-04 | `page_size` 上限 100，下限 1 | 15、25、30、33 |
| C-05 | 登录失败不区分「用户不存在」与「密码错误」，统一 `40103` | 2 |
| C-06 | **对"他人资源"统一返回 `404` / `40401`**，不返回 403；`40301` 仅用于"已认证但角色不足" | 12、13、14、16、17、20、22、31、34 |
| C-07 | 破坏性操作与全局配置变更写入 `operation_log` | 7、9.4、9.5、9.6、9.8、9.9 |
| C-08 | 图像二进制端点响应带 `Cache-Control: private`，`Content-Type` 由实际存储格式决定 | 12、13 |
| C-09 | 上传部分失败返回 HTTP 200 与 `failed[]`；全部失败返回首错码对应状态 | 9 |
| C-10 | 游客试用额度在实际识别成功后才扣减，上传本身不扣减 | 9、10、11 |
| C-11 | 主键对外类型为 string 标识，`species_id` 为整数 | 全部 |
| C-12 | **`species_id` 恒等于 `class_index`**（0 基，`0`～`22`），两者是同一数值的不同称呼 | 10、11、16、20、22、25 |
| C-13 | 「已产生识别记录的图像」不可删除，须走记录的软删除 | 14、17、18 |
| C-14 | 图像资产的创建按 `(user_id, content_hash)` 复用，相同内容的重复上传返回既有 `image_id` 与 `reused: true` | 9 |

> **C-06 的取值说明（V1.1 更正）**：本契约取 **「统一优先 404」**。理由是：若对他人的资源返回 `403`，攻击者可通过"403 还是 404"的差异**反推某个 ID 是否真实存在** —— 这恰恰违反 PRD「防 ID 枚举」的本意。返回 `404` 使"不存在"与"无权访问"不可区分。
>
> **V1.0 曾写作"统一优先 403"，方向恰好相反，属表述错误**。实现按 404 落地（见 `assert_can_access` 与各归属校验点），V1.1 已更正为与实现一致的 404。`40301` 的适用场景收窄为两类：① 非管理员访问管理端点；② 管理员对自身账号执行禁止操作（如删除自己）。
>
> **C-12 的取值说明（V1.1 更正）**：`species_id` **等于** `class_index`，**不是** `class_index + 1`。实测验证：`GET /api/species/0` 返回 `class_index = 0`（网纹宅泥鱼），`/api/species/2` 返回 `class_index = 2`（长棘光鳃鱼）。V1.0 的 `+1` 表述错误，若照此实现会导致**全表物种错位一格** —— 这是本组约束中最危险的一处，已由 `backend/tests/test_nfr_audit.py` 的 `class_index` 对齐断言守护。
>
> **C-14 的实际影响**：该复用行为会让"上传一张与既有图字节相同的图"返回**既有** `image_id`。若该图已识别，则对它执行删除会返回 `42201`（受 C-13 约束）。**测试与联调时须特别注意**：想验证"删除未识别图"，必须上传一张**内容未出现过**的图，否则会拿到旧资产。
